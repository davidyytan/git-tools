# Contributing to Git Tools

`git-tools` supports multiple LLM providers, prompt files, workflow examples, and a Git Flow-oriented release model. Keep changes aligned across code, docs, prompts, and tests.

## Development Setup

```bash
git clone https://github.com/<your-user>/git-tools.git
cd git-tools

uv sync
uv run git-tools settings
```

Use `uv run git-tools` to exercise the working checkout. To install the CLI as an editable tool, use `uv tool install -e .`.

For provider configuration, environment files, and interactive settings, see [Configuration](configuration.md). Provider metadata and static fallback models live in `git_tools/settings/mappings.py`; there is no `mappings.json` to copy.

## Branch and PR Flow

Normal code changes should start from `develop`:

```bash
git checkout develop
git pull origin develop
git checkout -b feature/<name>
```

Use `bugfix/<name>` for bug fixes. Reserve `release/*` and `hotfix/*` for the Git Flow release process.

Use Conventional Commit titles for normal PRs into `develop`. Start, Release, Hotfix, and Backmerge PRs use fixed workflow titles generated by `git-tools pr`, not Conventional Commit-style titles. See [Git Flow Guide](git-flow-guide.md) for the release policy and [Usage](usage.md) for commands and flags.

## Commits

Use Conventional Commit headers for normal code changes:

```text
type(scope): description
```

Common types are `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, and `ci`.

For normal feature and bugfix work, prefer using the tool:

```bash
git add -A
uv run git-tools commit
```

The commit-side workflow helper is the empty release opener, `git-tools commit --workflow-kind open-release`. See [Usage](usage.md) for details.

## Pull Requests

Describe the change, its motivation, and how you validated it. PR output should not include `## Related Issue` or `Issue: #...` placeholders.

For platform setup, branch policies, and complete workflow procedures, use the [GitHub guides](github/README.md) or [Azure DevOps guides](azure-devops/README.md). Avoid duplicating their command sequences here.

## Validation

Before opening a PR, run:

```bash
uv run python -m unittest discover -s tests
git diff --check
```

If you change provider configuration, prompt files, or workflow examples, also check the related docs and tests.

## Keeping Things In Sync

When you change one of these areas, update the others in the same PR when needed:

- generator packages in `git_tools/generators/<name>/`; keep each package's `__init__.py` re-exports stable, because `cli.py`, the CI adapters, and tests import `git_tools.generators.<name>` by that path (see [code layout](architecture.md))
- provider settings in `git_tools/settings/`
- provider and model definitions in `git_tools/settings/mappings.py`
- user-facing env examples in `git-tools.env.example`
- prompt files in `git_tools/prompts/`
- workflow examples in `.github/workflows/` and `.azure/workflows/`
- docs in `README.md`, `docs/usage.md`, `docs/git-flow-guide.md`, `docs/github/`, and `docs/azure-devops/`

Link directly to canonical guides; do not reintroduce legacy forwarding pages. If the change affects CLI behavior, add or update tests in `tests/`.
